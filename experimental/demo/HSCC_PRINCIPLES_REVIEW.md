# 按 HSCC 新设计准则审查 FAIRY2.0

审查日期：2026-11-16。对象：FAIRY 0.4.1 / Runtime schema 4。

**后续状态：本报告的七项发现已在 0.5.0 逐项处理，见 [修复与验收](HSCC_FIXES.md)。下文保留修复前的反例和判断，不代表当前缺陷状态。**

结论：当前实现保留了统一时钟、公共执行入口、普通拒绝回滚和严格回放等正确方向；但按新的失败反例审查，仍有 **1 项 P1 中断一致性问题、3 项 P2 功能/诊断缺陷，以及 3 项设计或验收缺口**。现有 274 项测试全部通过不能覆盖这些新增反例。当前适合继续收尾，不宜据此扩展到历史全部 L3-mini 或宣称农艺 Oracle 已验收。

## 范围与方法

依据：[HSCC 失败教训与 FAIRY2.0 设计准则](../HSCC失败教训与FAIRY2.0设计准则.md)。检查 `fairy/acps`、`fairy/events`、`fairy/agents`、`evaluate`、CLI、现有测试及历史验收证据。

本轮做代码检查、完整回归和无模型凭证的定向探针；没有修改生产实现，没有调用真实模型，没有重跑 HSCC 实验。探针中的受控中断是故障注入，不声称已观察到真实用户运行损坏。未接入的多品种、补种、施肥、异步装备和多农场不作为已实现功能报错，也不能视为已满足对应准则。

## 1. P1：操作中断绕过回滚，保存的快照可能无法恢复

位置：[Runtime.invoke](../fairy/events/session.py:87)、[执行循环](../fairy/agents/loop/controller/run.py:55)、[CLI 保存](../interface/cli/__main__.py:79)。对应准则：拒绝/失败原子性、跨日恢复、用户中断归档。

`invoke()` 和 `run_agent()` 只捕获 `Exception`；`KeyboardInterrupt` 不属于该分支。CLI 的 `finally` 仍保存产物，但不保证正在执行的事务已经回滚。

**实际复现：** 在 Native L1 的一次日结算完成更新后注入 `KeyboardInterrupt`：

```text
runtime.now     = 2026-05-09T07:00:00+08:00
backend.next_day = 2026-05-10
末事件           = operation_requested
恢复结果         = Backend clock disagrees with runtime clock
```

另在模型决策阶段注入中断，运行仍为 `done=False`，没有中断终止记录，产物无法直接区分“人工检查点”与“用户中断”。两者来自同一中断处理缺口。

**影响：** 已有“普通异常回滚”和“成功作业后恢复”测试不能证明 Ctrl-C 安全。若中断落在物理效果和时钟/事件提交之间，保存动作本身并不构成可恢复保障。此项不涉及对 SIGKILL 或掉电的保证。

**建议：** 在事务边界专门处理可捕获中断，先恢复到完整提交边界，再向上层传播；在控制器/CLI 明确记录中断原因及可恢复状态。不能只捕获后吞掉中断，也不能保存半提交状态并标记成功。新增“结算更新后中断”和“作业执行中断”的恢复反例。

## 2. P2：L3 Oracle 忽略场景单次推进上限

位置：[SeasonOracle.wait](../fairy/agents/loop/controller/season_oracle.py:13)。对应准则：公共契约、Oracle 可表达性和合法参数。

等待只取 `min(48, 剩余小时)`，没有纳入 `scenario.max_advance_hours`。场景声明和运行时 schema 支持更小上限，因此策略与执行契约不一致。

**实际复现：** 只把同一 L3 的 `max_advance_hours` 改为 12，保持其余配置，Oracle 完成建植后连续请求 48 小时；三次拒绝后以 `tool_error_budget` 结束，停在 5 月 5 日，未进入生长季。此时工具 schema 已正确声明 12 小时上限。

**建议：** Oracle 按场景上限、剩余期限和自身目标共同分段；验证较小单次上限下仍能推进。分段会增加所需调用数，测试必须给出与任务相称的预算，不能用固定 400 次保证所有有效配置都可完成。

## 3. P2：恢复了物理状态，但没有恢复模型的公开上下文

位置：[run_agent 的 history 初始化](../fairy/agents/loop/controller/run.py:22)、[公共上下文](../fairy/agents/loop/context/public.py:10)、[CLI resume](../interface/cli/__main__.py:61)。对应准则：状态交接、公开证据保留和恢复语义。

每次进入 `run_agent()` 都设置 `history=[]`。`Runtime.from_state()` 保留了事件和物理状态，但新的模型首请求没有重建此前的公开请求/结果。L3 的播种/收获覆盖能由事件重新汇总，库存、装备电量、近期观测和失败反馈却不在该汇总中。

**实际复现：** 检查库存和两垄作物后保存，再恢复并进入同一循环。恢复前两对公开历史，恢复后首请求为零对；库存和作物观测回执均未出现。相关成功回执仍完整存在于事件中，因此不是原始日志缺失。

**影响：** 物理继续执行的一致性不等于智能体信息连续性。恢复后需要重新查询，会改变决策机会、工具预算和历史条件；普通运行中历史淘汰也没有独立的近期观测/未解除阻塞摘要。这不是隐藏状态泄漏问题，而是公开证据丢失。

**建议：** 从已记录公开请求/结果重建有限上下文，不重调 LLM，也不读取 audit 补真值；明确观测时间和过期规则。若选择冷启动续跑，应作为显式模式记录，不能默认为与连续智能体运行等价。模型累计用量和本段用量也应分别保留。

## 4. P2：不同协议错误被折叠成 UNKNOWN_TOOL

位置：[LLMAdapter.decide](../fairy/agents/models/llm/adapter.py:74)、[统一无效响应入口](../fairy/agents/models/llm/adapter.py:103)。对应准则：协议诊断、错误分类与失败归因。

当前会安全拒绝异常响应，但所有失败都转成虚构工具 `invalid_model_response`，再由运行时返回 `UNKNOWN_TOOL`。未记录该次实际 finish_reason、原始调用数量和具体解析失败原因。

**实际复现：** 空 choices、空 stop、`length` 截断的完整 JSON 调用、一次返回两个调用，四类响应最终得到完全相同的请求和错误。已检查元数据也不能区分这些原因。

**影响：** 不会因此错误执行动作，但协议故障会占用业务工具错误额度；保存轨迹后难以追溯是模型提前停止、服务截断、调用数量违规还是参数解析失败。HSCC 的 MTP/空响应类问题将再次难以定位。

**建议：** 在模型调用审计中保存脱敏原因码、finish_reason、raw/effective 调用数量、用量及执行关联；区分协议与业务错误预算。完整请求/响应正文按隐私和体积策略另存，不能把凭证或服务异常原文发送给模型。保持非法响应不产生物理效果。

## 5. 设计缺口：没有长期停滞诊断，只有最终预算截止

位置：[执行循环](../fairy/agents/loop/controller/run.py:26)、[上下文进度](../fairy/agents/loop/context/public.py:16)。对应准则：时间流逝与有效进展分离。

当前不存在长期停滞分类：反复读取、巡检/充电交替、短等待和实际任务进展没有独立统计。L3 只保留播种/收获覆盖与入库次数；总预算仍能阻止无限循环，但不能解释为什么停滞。

**实际复现：** 模拟模型连续调用 `inspect_inventory` 30 次，时间停在 `2026-05-05T07:00:00+08:00`，零工具错误，仅记录 `step_budget`。没有独立的无时间进展/无任务变化诊断。该探针证明机制缺失，不预测真实模型必然如此选择。

**建议：** 先做只读诊断，记录调用窗口中的仿真时长、任务覆盖变化、物料变化、重复失败与无操作；必要提示必须仅依赖公开事实。不要把自动强制等待、禁止合法复查或由运行时补做农事当作修复。以真实模型失败场景另验策略效果。

## 6. 验收缺口：保留了历史天气，未保留 R5/R6 干旱挑战的阶段关系

位置：[Native 全季阶段与生长](../fairy/acps/backends/biology/native/season.py:152)、[当前场景](../evaluate/scenarios/lib/l3/soybean_full_season.py:30)、[既有过程边界](../fairy/acps/backends/biology/native/SEASON_AUDIT.md)。对应准则：农艺因果链与模型校准分离。

历史选中天气的目标干旱事件从 8 月 1 日开始，来源 profile 标记为 `r5_r6_waterlimited_dry_spell`。本轮用当前公开操作整田建植、无灌溉、逐日观察，22 号垄首次观测日期为：

| 阶段 | 日期 |
| --- | --- |
| R5 | 2026-07-15 |
| R6 | 2026-07-23 |
| R7 | 2026-08-01 |
| R8 | 2026-08-05 |

因此沿用事件开始时，代表垄已进入 R7，并非目标 R5/R6。阶段日期是当前固定输入下的轨迹证据，不是田间观测或所有播期的结论。历史来源为 `reference/FAIRY-test_Knowledge/fairy/physics/profiles.py:456`，仅作只读审计。

**影响：** 现有测试证明灌溉改变土壤以及工程收储闭环，但没有证明历史关键期挑战被等价重建。既有文档已声明阶段可能不同和模型未校准；本项把这种局限具体化，不将其追溯为违反此前用户限定的工程验收。

**建议：** 先确定当前场景是工程闭环还是农艺挑战。若保留后者，验证代表性播期的阶段—天气—胁迫—干预响应，并冻结同一外生天气做策略对照；不能为每个候选移动天气。当前 `stored>0` 的成功条件保留为限定工程门槛，不应用作产量优化或最省水 Oracle 的充分目标，也不随意添加无来源的最低产量阈值。

## 7. 设计缺口：版本与输入指纹已有，但执行身份和证据保留仍不完整

位置：[artifact](../fairy/events/artifacts.py:15)、[write_json](../fairy/events/artifacts.py:27)、[CLI 输出](../interface/cli/__main__.py:66)。对应准则：不可变实验产物、可追溯身份和上下文审计。

- 已保存 Python、若干依赖版本、FAIRY 手动版本、场景和绑定指纹；没有自动保存实际源码树/文件指纹或 Git 提交及 dirty 内容。相同 0.4.1 版本下的源码编辑不能仅靠这些身份识别。
- 输出采用原子替换，能减少半个 JSON 文件，但不等于不可变存储；默认输出路径可复用，进度日志会先清空，历史失败可能被后续运行覆盖。
- `max_context_chars` 约束的是构建的上下文字典，不是 SDK 最终请求体或服务 token；原始历史淘汰数、实际发送大小和逐次上下文指纹未记录。不能将当前字符预算视为模型上下文不溢出的证明。

**建议：** 区分开发快照覆盖和正式 attempt 归档；正式运行生成唯一身份并默认拒绝覆盖。记录源码、数据和评价器身份，保存逐次脱敏调用/上下文摘要及用量。不要求现在移植完整 HSCC 队列，但应先防止单任务证据丢失。

## 已满足的方向及其边界

| 准则 | 当前依据 | 结论边界 |
| --- | --- | --- |
| L1/L3 共用执行骨架 | 同 Runtime、注册表、循环、CLI、恢复和回放 | 不等于原历史 L3 全部能力已迁入 |
| 任务事实与模型结束分开 | 结构化评价，模型结束不自动成功，CLI run 按结果返回 | 中断分类仍有第 1 项缺口 |
| 公共单位与局部灌溉核算 | mm/m²/m³，空间配额，待结算队列 | 尚无施肥/药液等新契约 |
| 普通失败回滚 | 非法请求、普通执行异常、跨日失败已有测试 | 不覆盖 KeyboardInterrupt |
| 不引入历史空批干燥成功 | 空容器/无需干燥明确拒绝，粮食按干物质和水记账 | 尚非完整物料批次与物流模型 |
| 公开/特权路径分开 | LLM 不得到 Runtime/audit，Oracle 显式特权 | 模型调用审计和续跑公开上下文需补齐 |
| 独立后端 | WOFOST 自有水分生长，L3 不支持时拒绝 | WOFOST L3、多作物和多农场未接入 |
| 严格回放 | 新实例重执行并比较事件、状态、审计和指标 | 回放通过不证明任务策略或农艺模型有效 |
| 无历史知识/评分隐式注入 | 默认无 detail/library/Oracle 轨迹和 FOS 等综合分 | 未接入 RAG 不算通过知识兼容性测试 |
