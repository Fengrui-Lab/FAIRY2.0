# HEINONG58真实LLM验证：normal、R1、R5与双阶段干旱

2026-11-16，`kun`分支，FAIRY 0.6.0 / 状态schema6 / Native全季后端。

**本轮工程任务3组通过、1组失败；四条最终轨迹均通过新进程严格回放。模型能执行补水和收储，但尚未表现出可靠、及时的干旱观测与补水闭环。**

## 方法与可复核边界

使用当前服务公布并在实际响应中确认的 `Qwen3.6-35B-A3B-FP8`，现有 `chat_tools_v5` 适配器。
四组从相同播种前初态开始，仅固定扰动窗口的降雨不同。四组第一个实际模型请求的载荷指纹完全一致，
没有场景名称、未来干旱日历、Oracle轨迹或固定剂量提示。normal管理知识模板尚未注入模型，本轮没有RAG。

- temperature 0.1，关闭thinking，输出上限2048 tokens。
- 每场景累计最多400次决策、10次工具错误、3次已识别协议错误；近期历史20轮，公开上下文预算60000字符。
- 请求超时240秒。初段墙钟预算3600秒；实际共享服务延迟较高，在预算届满前统一安全挂起，官方resume入口续跑（续段7200秒）。
- 续段决策上限为400减初段调用数，包含已中断请求；工具错误额度和完整物理状态继续累计。
- 四个检查点均严格回放通过，恢复后完整状态与保存状态相等；四组续段首个实际请求均与中断请求载荷指纹相同。
- 初段退出130是测试控制挂起，不是模型主动结束或任务失败。每组是一条分两段执行的真实策略轨迹，不宣称为未中断单次运行。
- 模型仅获得任务、工具定义、公开状态、观测及回执。没有人工补做农事动作，没有修改场景、提示或剂量来促成成功。
- 四组并发使用共享服务。报告耗时不能作为隔离条件下的模型性能排名；每场景仅一条轨迹，不估计稳定成功率。

原始配置、恢复谱系、调用指纹和环境版本均保留在[证据目录配置](../../.runs/hn58_real_llm_20261116/config.json)
及[续跑配置](../../.runs/hn58_real_llm_20261116/continuation_config.json)。

## 补水是否依据观测、是否及时

| 场景 | 已发生的补水行为 | 观测依据及判断 |
|---|---|---|
| normal | 5月12日整田50mm | 当时可见土壤读数来自5月5日，VWC 0.310，已过7天；补水前没有复查 |
| R1 | 7月20日整田50mm | 先获得当日VWC 0.257，再补水；有新观测依据，但距6月13日干旱结束已超过一个月 |
| R5 | 7月20日50mm、21日10mm | 全程没有土壤观测；补水晚于7月9日干旱结束，未形成水分反馈闭环 |
| 双阶段 | 无 | 全程无土壤观测；第一干旱完整结算12天，第二干旱只结算3/10天即协议终止 |

R1和R5均走完整个对应干旱窗口，但窗口中没有土壤观测或灌溉。
模型主要反复检查作物阶段，而该工具只提供阶段与成熟期籽粒含水率，不能代替根区含水率。
因此本轮证明了模型能够调用补水、纠正参数和完成多数收储任务，尚未证明它能够可靠识别并及时应对干旱。

三组出现补水的场景，都首先请求单次60mm，与工具schema声明的最大50mm冲突；被拒绝后才修正。
这些拒绝未产生物理副作用，严格回放重现了同样的错误和纠正。

## 用反事实区分“有灌溉”与“有效灌溉”

在新实例保留其他已记录动作，删除指定的成功灌溉请求，重新执行和严格回放；这些是固定动作的诊断性仿真，
不是额外真实LLM轨迹，不重新生成策略，不估计最优剂量。

| 删除的实际补水 | 节省水量 mm | 相对原轨迹少入库干物质 kg |
|---|---:|---:|
| normal全部补水 | 50 | 0 |
| R1全部晚期补水 | 50 | 46.410 |
| R5全部晚期补水 | 60 | 71.589 |
| R5第二次补水 | 10 | 0 |

normal灌溉结算日，50mm对应46mm排水与4mm施用损失；去掉该补水，最终入库结果不变。
R5第二次10mm对应9.2mm排水与0.8mm损失；去掉它，同样不改变最终入库结果。
这提供了直接的水量浪费证据，不能仅因守住60mm额度就认定用水合理。

前轮同版本、同场景输入的已知窗口固定探针：R1在窗口中补20mm入库2321.600kg，R5补20mm入库2902.062kg；
均用水更少、实际入库量更高。该探针知道事件窗口，只证明模拟器中存在更有效的补水时机，
不是相同信息条件下的Agent排名或全局最优解。早期胁迫产生的过程影响不能靠晚期补水简单追补。

## 双阶段失败的直接原因

最后一次模型响应的content为：

```text
<tool_call>def call="inspect_inventory">
</function>
</tool_call>
```

实际返回 `finish_reason=stop`、结构化 `tool_calls=[]`、输出14 tokens。
[适配器](../fairy/agents/models/llm/adapter.py)将非空的正常stop文本统一视为 `model_finished`，
没有把工具标记文本识别为协议错误，所以既没有触发协议反馈重试，也没有增加protocol_errors计数。
运行于7月3日结束，64垄已种植、0垄收获、水额仍余60mm；没有耗尽400次决策额度、没有服务异常或长度截断证据。

我们按事件重建了最后请求前的公开上下文，并用同一适配器在无网络捕获模式重建载荷。
其指纹与真实最后请求完全一致，确认模型当时仍可见64垄未收获及0次入库，
虽只保留20轮近期历史，也没有丢失全局任务进度。不能把这次失败归因于进度被裁剪，
也不能断言模型认为任务已经完成；文本更像是试图继续调用库存工具，但格式不合法。

**应优先改进的协议处理**：发现明确工具标记但无结构化调用时，作为受限协议错误反馈并重试；
不直接执行或自动修补文本中的工具。保留正常纯文本结束语义及错误预算。
本轮未修改适配器或重新启动失败场景以替换结果。

## 其余问题与下一轮重点

1. **目标与能力检查脱节。** 当前任务判据要求收储、守恒和水额，没有明确水分管理目标；不及时补水也可能通过。
   下一轮应保留工程指标，另明确基于公开观测的水分管理目标或评价，不追加隐藏产量分。
2. **农艺知识尚未接入。** normal管理模板目前只作为声明和审计信息，未传入LLM。应另设共享知识增强对照，
   提供阶段监测原则，不提供隐藏干旱日期、Oracle轨迹或答案剂量。
3. **收获前置条件表述不足。** normal、R1均在R7尝试收获被拒绝；现有工具只写“成熟”，而后端要求R8。
   应把固定前置条件明确写入公共工具契约。容量拒绝后模型能缩小作业范围；没有公开田间可收获质量，不能把所有容量试探都归为模型规划错误。
4. **观测和上下文效率。** normal进行了100次整田作物检查，约443万输入tokens；需考虑保真汇总观测、显式观测年龄和减少重复回执。
   共享服务排队和输入量共同构成性能风险，本轮没有隔离测量其各自影响。
5. **Oracle不是上限。** 现有策略不处理R1，仅在R5/R6且内部VWC低于0.20时选首个干旱垄补15mm，登记后先等待。
   双阶段只覆盖6垄，各15mm，全田平均1.40625mm；R1、R5单阶段均未补水。应补强整田分配或搜索策略，保留固定干预探针作因果参照。
